Historias de Usuario — Sistema de Notificación Automatizada de Parches de Vulnerabilidades

> **Proyecto**: VulnPatchNotifier — Tesis UTN FRM
> **Fecha**: 2026
> **Ordenamiento**: Por orden lógico de implementación (dependencias resueltas primero)


Actores del Sistema

| Actor                      | Descripción                                                                                   |
| -------------------------- | --------------------------------------------------------------------------------------------- |
| **Sistema**                | Pipeline automatizado n8n: ejecuta workflow, recolecta, correlaciona, prioriza, notifica      |
| **Analista de Seguridad**  | Recibe alertas, triagea, reconoce, marca falsos positivos, coordina remediación               |
| **Gestor de IT**           | Aplica parches, documenta remediación, registra patch_version y verification_method           |
| **Responsable Org.**       | Consume métricas de postura de seguridad: MTTD, MTTR, SLA compliance, tendencias             |
| **Administrador**          | Mantiene inventario CPE, configura workflows, gestiona entorno Docker, ajusta parámetros      |

EPIC 00 — Infraestructura y Setup

US-000: Entorno Docker Compose

- **Título**: Configuración del entorno base con Docker Compose
- **Historia**: Como **Administrador**, quiero levantar todo el entorno del sistema con un único comando, para reproducir el ambiente de desarrollo/producción de forma portable.
- **Prioridad**: Alta
- **Dependencias**: Ninguna

**Criterios de Aceptación**:
- [ ] GIVEN el archivo docker-compose.yml y .env configurado, WHEN ejecuto `docker-compose up -d`, THEN los tres contenedores (n8n, postgres, redis) están corriendo sin errores.
- [ ] n8n es accesible en http://localhost:5678 con autenticación básica.
- [ ] PostgreSQL está accesible desde n8n en el host `postgres` puerto 5432 dentro de la red Docker.
- [ ] Redis está accesible desde n8n en el host `redis` puerto 6379 dentro de la red Docker.
- [ ] El contenedor PostgreSQL persiste datos en un volumen Docker nombrado para sobrevivir reinicios.
- [ ] `docker-compose down` detiene todos los contenedores sin errores.

**Notas Técnicas**:
- Servicios: n8n:latest (o tag específico 1.x), postgres:16, redis:7
- Networks: red privada `vuln-network` — PostgreSQL y Redis NO expuestos al host
- Volumes: postgres_data, n8n_data
- Health checks: postgres con `pg_isready`, n8n con HTTP GET /healthz

EPIC 01 — Recolección de CVEs (Etapa 1)

US-001: Schedule Trigger Diario

- **Título**: Trigger cron de ejecución diaria
- **Historia**: Como **Sistema**, quiero ejecutar el pipeline de recolección automáticamente cada día a las 02:00 UTC, para asegurar que ninguna vulnerabilidad publicada ese día quede sin procesar.
- **Prioridad**: Alta
- **Dependencias**: US-000d

**Criterios de Aceptación**:
- [ ] GIVEN el workflow activo en n8n, WHEN llegan las 02:00 UTC, THEN el workflow se ejecuta automáticamente sin intervención humana.
- [ ] El Schedule Trigger está configurado con expresión cron `0 2 * * *`.
- [ ] El workflow puede ejecutarse también manualmente desde n8n UI para testing (botón "Execute Workflow").
- [ ] Si el workflow falla, n8n no reintenta automáticamente (el sistema maneja reintentos explícitamente en US-041).

**Notas Técnicas**:
- Nodo: Schedule Trigger (tipo Cron)
- Expresión cron: `0 2 * * *`
- RN-RC01

US-002: Consulta a NVD API

- **Título**: Recolección de CVEs desde NVD API 2.0
- **Historia**: Como **Sistema**, quiero consultar la NVD API 2.0 con el rango de fechas de las últimas 24 horas, para obtener todos los CVEs publicados hoy.
- **Prioridad**: Alta
- **Dependencias**: US-001, US-000c

**Criterios de Aceptación**:
- [ ] GIVEN el workflow ejecutándose, WHEN consulta NVD API, THEN la request incluye pubStartDate y pubEndDate calculados dinámicamente.
- [ ] La API key se incluye en el header `x-api-key` (no en query params).
- [ ] El parámetro `resultsPerPage=2000` está configurado.
- [ ] Si la API retorna HTTP 200 con array vulnerabilities no vacío, el workflow continúa al siguiente nodo.
- [ ] Si la API retorna HTTP 403 (API key inválida), el workflow registra FAILED en audit_log con mensaje descriptivo.
- [ ] Si la API retorna HTTP 503 o timeout, el workflow registra FAILED en audit_log y re-intenta una vez tras 5 minutos (RN-RC07).

**Notas Técnicas**:
- Endpoint: `GET https://services.nvd.nist.gov/rest/json/cves/2.0`
- Params: `pubStartDate={{ $now.minus({days:1}).toFormat('yyyy-MM-dd') }}T00:00:00.000&pubEndDate={{ $now.toFormat('yyyy-MM-dd') }}T23:59:59.999&resultsPerPage=2000`
- RN-RC02

US-003: Parseo y Normalización de Respuesta NVD

- **Título**: Parsing del JSON de NVD y normalización de campos
- **Historia**: Como **Sistema**, quiero extraer y normalizar los campos relevantes de cada CVE retornado por NVD, para preparar un objeto limpio e insertable en PostgreSQL.
- **Prioridad**: Alta
- **Dependencias**: US-002

**Criterios de Aceptación**:
- [ ] GIVEN la respuesta JSON de NVD, WHEN ejecuta el Function node de parseo, THEN produce un objeto por CVE con los campos: cve_id, description (en inglés), cvss_v3_base_score, cvss_v3_vector, cvss_v3_severity, cvss_v2_base_score, cwe_id, published_date, last_modified_date, configurations (JSON string), references (JSON string).
- [ ] Si el CVE no tiene métricas CVSS v3 pero tiene v2, se usan los campos de v2 como fallback (RN-RC05).
- [ ] Si el CVE no tiene ningún score CVSS, los campos numéricos quedan en null (no falla el nodo).
- [ ] La descripción se extrae priorizando el idioma 'en'; si no existe, se usa el primer idioma disponible.
- [ ] configurations y references se serializan como JSON string para almacenamiento en columnas JSONB.

**Notas Técnicas**:
- Función JavaScript en n8n Function Node
- Path CVSS v3: `cve.metrics?.cvssMetricV31?.[0]?.cvssData`
- Path CVSS v2: `cve.metrics?.cvssMetricV2?.[0]?.cvssData`
- Path description: `cve.descriptions?.find(d => d.lang === 'en')?.value`
- RN-RC05

US-004: Upsert de CVEs en PostgreSQL

- **Título**: Inserción idempotente de CVEs en base de datos
- **Historia**: Como **Sistema**, quiero insertar los CVEs parseados en la tabla cves de forma idempotente, para que re-ejecuciones del workflow no generen duplicados.
- **Prioridad**: Alta
- **Dependencias**: US-003, US-000a

**Criterios de Aceptación**:
- [ ] GIVEN los CVEs normalizados, WHEN ejecuta el nodo PostgreSQL, THEN inserta cada CVE con status='unprocessed'.
- [ ] Si el cve_id ya existe (conflicto en UNIQUE constraint), actualiza description, last_modified_date, references y updated_at (ON CONFLICT DO UPDATE).
- [ ] Si el CVE ya tiene status='correlated' o 'prioritized', el upsert NO resetea su status.
- [ ] La cantidad de CVEs insertados/actualizados se reporta en el audit_log (records_processed).
- [ ] El nodo falla explícitamente (y registra FAILED en audit_log) si PostgreSQL no está disponible.

**Notas Técnicas**:
- SQL: `INSERT INTO cves (...) ON CONFLICT (cve_id) DO UPDATE SET description=EXCLUDED.description, last_modified_date=EXCLUDED.last_modified_date, references=EXCLUDED.references, updated_at=NOW() WHERE cves.status='unprocessed'`
- RN-RC03

US-005: Paginación de NVD API

- **Título**: Manejo de paginación cuando NVD retorna más de 2000 CVEs
- **Historia**: Como **Sistema**, quiero paginar las requests a NVD API cuando el total de CVEs del día supera 2000, para no perder vulnerabilidades publicadas ese día.
- **Prioridad**: Media
- **Dependencias**: US-002, US-003

**Criterios de Aceptación**:
- [ ] GIVEN una respuesta NVD donde totalResults > 2000, WHEN el workflow detecta la condición, THEN ejecuta requests adicionales con startIndex incrementado en 2000 por iteración.
- [ ] El loop continúa hasta que startIndex >= totalResults.
- [ ] Todos los CVEs de todas las páginas se acumulan y se procesan por el nodo de parseo.
- [ ] El audit_log registra el total de CVEs procesados (suma de todas las páginas).

**Notas Técnicas**:
- Nodo IF: `$json.totalResults > ($json.startIndex + $json.resultsPerPage)`
- Incrementar startIndex y hacer nueva request HTTP con startIndex actualizado
- RN-RC04

US-006: Registro en Audit Log

- **Título**: Auditoría de cada ejecución de workflow
- **Historia**: Como **Administrador**, quiero que cada ejecución de workflow quede registrada en audit_log, para poder diagnosticar problemas y auditar el comportamiento del sistema.
- **Prioridad**: Alta
- **Dependencias**: US-004

**Criterios de Aceptación**:
- [ ] GIVEN cualquier ejecución del workflow de recolección (exitosa o fallida), THEN se inserta un registro en audit_log.
- [ ] El registro incluye: workflow_name='workflow-collection', execution_id (de n8n), status (SUCCESS/FAILED/PARTIAL), records_processed, error_message (si aplica), execution_time_ms, executed_at.

- [ ] status=PARTIAL: algunos CVEs fallaron pero al menos uno fue procesado exitosamente.
- [ ] status=FAILED: el workflow falló antes de procesar cualquier CVE (API no disponible, BD no disponible).
- [ ] El registro de audit_log se inserta incluso cuando el workflow falla (mediante nodo de error handling).

**Notas Técnicas**:
- SQL: `INSERT INTO audit_log (workflow_name, execution_id, status, records_processed, error_message, execution_time_ms)`
- RN-RC06, RN-RC07

US-008: Validación de CPE URI

- **Título**: Validación de formato CPE URI en inventario
- **Historia**: Como **Administrador**, quiero que el sistema valide el formato de los CPE URIs antes de aceptarlos, para evitar datos incorrectos que impidan la correlación.
- **Prioridad**: Alta
- **Dependencias**: US-007

**Criterios de Aceptación**:
- [ ] GIVEN un CPE URI con formato cpe:2.3:a:apache:http_server:2.4.49:*:*:*:*:*:*:*, WHEN se inserta, THEN se acepta correctamente.
- [ ] GIVEN un CPE URI con formato inválido (ej. apache:http_server:2.4.49), WHEN se intenta insertar, THEN se rechaza con mensaje de error.
- [ ] El CPE URI debe comenzar con `cpe:2.3:`.
- [ ] El CPE URI debe tener exactamente 13 componentes separados por `:`.

**Notas Técnicas**:
- Implementar como CHECK constraint en PostgreSQL: `CONSTRAINT valid_cpe_format CHECK (cpe_uri LIKE 'cpe:2.3:%')`
- Validación de 13 componentes: `array_length(string_to_array(cpe_uri, ':'), 1) = 13`
- RN-IN01, RN-IN06

US-009: Clasificación de Criticidad de Activos

- **Título**: Asignación de criticidad a activos del inventario
- **Historia**: Como **Administrador**, quiero clasificar cada activo por criticidad (CRITICAL/HIGH/MEDIUM/LOW), para que el motor de priorización pueda calcular el impact factor correcto.
- **Prioridad**: Alta
- **Dependencias**: US-007

US-036: Cálculo de MTTD

- **Título**: Query SQL para cálculo de Mean Time To Detect
- **Historia**: Como **Responsable Organizacional**, quiero consultar el MTTD promedio del sistema, para medir la velocidad de detección de vulnerabilidades aplicables.
- **Prioridad**: Alta
- **Dependencias**: US-016

**Criterios de Aceptación**:
- [ ] GIVEN datos en applicable_vulnerabilities y cves, WHEN ejecuta la query de MTTD, THEN retorna AVG de horas entre published_date del CVE y created_at de la correlación.
- [ ] El resultado es un valor numérico en horas con 2 decimales.
- [ ] La query soporta filtro por rango de fechas (últimos 30 días por default).
- [ ] Un MTTD < 4 horas indica que el sistema está cumpliendo el objetivo proyectado.

**Notas Técnicas**:
- SQL: `SELECT AVG(EXTRACT(EPOCH FROM (av.created_at - c.published_date))/3600) AS mttd_hours FROM applicable_vulnerabilities av JOIN cves c ON av.cve_id = c.id WHERE av.created_at >= NOW() - INTERVAL '30 days'`
