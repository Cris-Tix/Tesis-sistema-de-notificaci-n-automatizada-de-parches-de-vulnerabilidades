1. Visión General del Sistema

El Sistema de Notificación Automatizada de Parches de Vulnerabilidades es una solución de Security Orchestration orientada a reducir la ventana de exposición organizacional ante CVEs publicados. El sistema integra múltiples fuentes de inteligencia de amenazas (NVD API, Shodan, CISA KEV), las orquesta mediante n8n, y persiste el estado de correlación y remediación en PostgreSQL.

El pipeline opera de forma autónoma: se ejecuta diariamente a las 02:00 UTC, recolecta CVEs publicados en las últimas 24 horas, los correlaciona automáticamente contra el inventario de software de la organización usando nomenclatura CPE, calcula un score de riesgo multifactorial, y envía alertas contextualizadas por email y Slack a los equipos responsables.

1.1 Objetivos del Sistema

OBJ-02  Gestor de IT            Registrar el estado de remediación y marcar parches aplicados
OBJ-03  Responsable Org.        Visualizar métricas de SLA compliance y postura de seguridad organizacional
OBJ-04  Administrador           Configurar el sistema, mantener el inventario CPE, y gestionar workflows n8n
OBJ-05  Sistema                 Ejecutar el pipeline automatizado de 5 etapas sin intervención humana
OBJ-06  Sistema                 Garantizar trazabilidad completa del ciclo detección → notificación → remediación

1.2 Alcance v1.0

• Pipeline de 5 etapas orquestado en n8n: recolección → filtrado → correlación → priorización → alertas
• Integración con NVD API 2.0 para recolección de CVEs publicados en las últimas 24h
• Integración con Shodan API para verificación de exposición pública de activos
• Integración con CISA KEV Catalog (JSON feed) para detección de vulnerabilidades explotadas activamente
• Modelo de datos PostgreSQL con 5 tablas: cves, software_inventory, applicable_vulnerabilities, vulnerability_alerts, audit_log
• CPE matching con soporte de exact match, wildcard match, y version range matching (semver)
• Motor de priorización multifactorial con 5 factores ponderados (CVSS base, CVSS temporal, exposición, criticidad, KEV)
• SLA diferenciado por criticidad: Critical 24h, High 72h, Medium 7 días, Low 30 días
• Notificaciones via email (HTML con color-coding) y Slack (Block Kit con botón NVD)
• Tracking completo de remediación: acknowledged → in_progress → remediated
• Re-notificación automática ante vencimiento de SLA
• Métricas de SecOps calculables mediante queries SQL: MTTD, MTTR, SLA compliance, tasa de correlación, tasa de falsos positivos
• Despliegue completo con Docker Compose: n8n + PostgreSQL + Redis (cache de n8n)
• Audit log de cada ejecución del workflow con timestamps y conteo de registros procesados

FUERA DE ALCANCE: Remediación automatizada (aplicación automática de parches), validación post-patch,
integración con sistemas de ticketing (Jira/ServiceNow), scanner activo de vulnerabilidades,
integración con CVE Details (descartada por ausencia de API REST oficial — ver Sección 8.3 de tesis).

2. Arquitectura del Sistema

2.1 Pipeline de 5 Etapas — Flujo de Datos

El sistema implementa un pipeline secuencial de 5 etapas ejecutadas como workflows n8n independientes encadenados.
El flujo de datos es unidireccional: cada etapa produce output que alimenta la siguiente.
Ninguna etapa puede leer de una etapa posterior ni saltear una etapa anterior.

[DIAGRAMA: Pipeline de 5 Etapas]

ETAPA 1         ETAPA 2             ETAPA 3             ETAPA 4             ETAPA 5
Recolección  →  Filtrado/Norm.  →  Correlación  →  Priorización  →  Alertas
NVD API         Function Node       CPE Matching        Risk Score          Email + Slack
cves table      (JavaScript)        applicable_vuln     risk_score          vulnerability_alerts

Regla de oro — flujo de datos:
  Recolección → Filtrado → Correlación → Priorización → Alertas
Ningún workflow de una etapa posterior puede modificar datos de etapas anteriores.
Un workflow de Alertas nunca modifica la tabla cves. Un workflow de Correlación nunca envía notificaciones.

Etapa   Workflow n8n                Responsabilidad                             Escribe en
1       workflow-collection.json    Consulta NVD API, parsea, upsert CVEs       cves, audit_log
2       (integrado en Etapa 1)      Filtrado y normalización de JSON NVD         (en memoria)
3       workflow-correlation.json   CPE matching contra software_inventory       applicable_vulnerabilities
4       workflow-prioritization.json Calcula risk_score, asigna criticality tier  applicable_vulnerabilities (update)
5       workflow-alerts.json        Genera y envía alertas email + Slack         vulnerability_alerts

2.4 Motor de Priorización — Fórmula de Risk Score

Risk_Score = (0.35 × CVSS_base) + (0.25 × CVSS_temporal) + (0.20 × Exposure_factor)
           + (0.15 × Criticality_factor) + KEV_bonus

CVSS_temporal          = CVSS_base × Exploit_maturity_multiplier
Exploit_maturity_multiplier: Unproven/POC=0.90 | Functional=0.95 | High=1.00

Exposure_factor:       Visible en Shodan=10 | No visible=3
Criticality_factor:    CRITICAL=10 | HIGH=7.5 | MEDIUM=5 | LOW=2.5
KEV_bonus:             En CISA KEV=+2.0 | No en KEV=0

Risk_Score se cappea en 10.0.

Criticality_tier asignado por Risk_Score:
  CRITICAL  → score >= 8.5   → SLA 24 horas
  HIGH      → score 7.0–8.4  → SLA 72 horas
  MEDIUM    → score 5.0–6.9  → SLA 7 días
  LOW       → score < 5.0    → SLA 30 días

3. Workflows n8n — Especificación por Nodo

3.1 Workflow de Recolección (workflow-collection.json)

Nodo                    Tipo n8n            Configuración clave
Schedule Trigger        Cron                0 2 * * *  (02:00 UTC daily)
HTTP Request NVD        HTTP Request        GET https://services.nvd.nist.gov/rest/json/cves/2.0
                                            Params: pubStartDate, pubEndDate, resultsPerPage=2000
                                            Header: x-api-key: {{NVD_API_KEY}}
Function ParseNVD       Function (JS)       Extrae cve_id, description, cvssV3, configurations, references
                                            Maneja fallback a CVSS v2 si v3 no disponible
                                            Serializa configurations/references a JSON string
PostgreSQL Upsert       PostgreSQL          INSERT INTO cves ... ON CONFLICT (cve_id) DO UPDATE
                                            Actualiza description, last_modified_date, status
IF Pagination           IF                  totalResults > startIndex + resultsPerPage → paginar
Audit Log               PostgreSQL          INSERT INTO audit_log con conteo y execution_id

3.2 Workflow de Correlación (workflow-correlation.json)

Nodo                    Tipo n8n            Configuración clave
HTTP Trigger / Cron     Webhook / Cron      Encadenado desde workflow-collection vía HTTP Request
Query CVEs              PostgreSQL          SELECT * FROM cves WHERE status='unprocessed' AND DATE(published_date)=TODAY
Function CPE Match      Function (JS)       Por cada CVE: parsea configurations JSON
                                            Extrae CPEs del CVE (navega nodos AND/OR/MATCH)
                                            Compara contra software_inventory usando:
                                              1. Exact match
                                              2. Wildcard match (CPE termina en *)
                                              3. Version range match (semver con versionStartIncluding/versionEndExcluding)
                                              4. Fallback heurístico (sufijos distribución, 4 componentes, formato fecha)
                                            Asigna correlation_confidence: HIGH/MEDIUM/LOW
PostgreSQL Insert       PostgreSQL          INSERT INTO applicable_vulnerabilities (cve_id, software_id, ...)
                                            ON CONFLICT (cve_id, software_id) DO NOTHING
Update CVE Status       PostgreSQL          UPDATE cves SET status='correlated' WHERE id=...

3.3 Workflow de Priorización (workflow-prioritization.json)

Nodo                    Tipo n8n            Configuración clave
Query Applicable        PostgreSQL          SELECT av.*, c.cvss_v3_base_score, si.criticality, si.ip_address
                                            FROM applicable_vulnerabilities av JOIN cves JOIN software_inventory
                                            WHERE av.risk_score IS NULL
HTTP Shodan             HTTP Request        GET https://api.shodan.io/shodan/host/{ip}?key={{SHODAN_API_KEY}}
                                            Determina exposed = TRUE si IP aparece en Shodan
HTTP CISA KEV           HTTP Request        GET https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json
                                            (cacheado 24h) → verifica si cve_id está en la lista
Function Risk Score     Function (JS)       Implementa fórmula multifactorial
                                            Calcula CVSS_temporal con Exploit_maturity_multiplier
                                            Cappea en 10.0, asigna criticality_tier
Update App Vuln         PostgreSQL          UPDATE applicable_vulnerabilities SET risk_score, criticality_tier,
                                            shodan_exposed, kev_listed, exploit_available WHERE id=...
Update CVE Status       PostgreSQL          UPDATE cves SET status='prioritized'

3.4 Workflow de Alertas (workflow-alerts.json)

Nodo                    Tipo n8n            Configuración clave
Query Pending Alerts    PostgreSQL          SELECT av.*, c.*, si.* FROM applicable_vulnerabilities av
                                            JOIN cves c JOIN software_inventory si
                                            WHERE av.criticality_tier IS NOT NULL
                                            AND NOT EXISTS (SELECT 1 FROM vulnerability_alerts va WHERE va.applicable_vulnerability_id=av.id)
                                            ORDER BY av.risk_score DESC
Function Build Template Function (JS)       Genera HTML email con color-coding por criticality_tier
                                            Genera Slack Block Kit JSON con emoji por tier
Send Email              Send Email          SMTP con HTML template, to: security-team@org.com
HTTP Slack              HTTP Request        POST a SLACK_WEBHOOK_URL con Block Kit payload
PostgreSQL Insert Alert PostgreSQL          INSERT INTO vulnerability_alerts (applicable_vulnerability_id, alert_type, recipient, ...)

3.5 Workflow de Monitoreo SLA (workflow-monitoring.json)

Nodo                    Tipo n8n            Configuración clave
Cron SLA Check          Cron                0 * * * *  (cada hora)
Query Overdue           PostgreSQL          SELECT * FROM applicable_vulnerabilities av
                                            JOIN vulnerability_alerts va ON av.id=va.applicable_vulnerability_id
                                            WHERE CURRENT_TIMESTAMP > av.sla_deadline
                                            AND va.status NOT IN ('remediated','false_positive')
Function Re-notification Function (JS)      Genera mensaje de re-notificación con tiempo vencido
HTTP Slack Escalation   HTTP Request        POST a SLACK_WEBHOOK_ESCALATION_URL

6. Patrones Aplicados en el Proyecto

Patrón                      Capa                Descripción
Pipeline Pattern            Orquestación        5 etapas secuenciales e independientes orquestadas en n8n
Idempotent Processing       Colección/BD        INSERT ON CONFLICT DO UPDATE previene duplicados en cves
Upsert Pattern              BD                  Actualización segura en re-ejecuciones del workflow
Audit Trail                 BD                  audit_log registra toda ejecución: timestamp, status, count
SLA State Machine           BD/Alertas          vulnerability_alerts transiciona: notified→acknowledged→in_progress→remediated
Multifactorial Scoring      Priorización        5 factores ponderados con pesos configurables
Caching                     Priorización        CISA KEV cacheado 24h para evitar requests redundantes
Heuristic Fallback          Correlación         CPE matching degradado con confidence=MEDIUM/LOW para versiones no-semver
Separation of Concerns      Workflows           Cada workflow tiene responsabilidad única e interfaces definidas
Infrastructure as Code      Docker              docker-compose.yml + .env.example definen entorno reproducible

7. Métricas de Evaluación (SecOps KPIs)

Métrica             Definición                                          Fórmula SQL clave                       Target
MTTD                Tiempo desde publicación CVE hasta correlación      AVG(av.created_at - c.published_date)   < 4 horas
MTTR Critical       Tiempo desde notificación hasta remediación         AVG(remediation_completed_at - sent_at) < 24 horas
Tasa Correlación    % CVEs con activo afectado identificado             CVEs correlacionados / Total aplicables  > 95%
SLA Compliance      % remediados dentro de SLA objetivo                 Remediados en SLA / Total remediados    > 85%
Falsos Positivos    % alertas marcadas como no aplicables               false_positive / Total alertas          < 5%
Cobertura Inventario % activos con CPE preciso en inventario            Activos con CPE / Total activos         > 90%
